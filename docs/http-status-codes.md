# HTTP статус коды — Snaptix Backend

Руководство по выбору HTTP статус кодов для REST API. Основано на RFC 9110, RFC 7807, RFC 4918 и практике Stripe, GitHub, Google Cloud, Auth0, AWS Cognito, Microsoft Graph.

---

## Дерево решений

```
Запрос обработан успешно?
├─ Да
│   ├─ Создан новый ресурс прямо сейчас → 201 Created
│   ├─ Обработка асинхронная (очередь, фоновая задача) → 202 Accepted
│   ├─ Есть тело ответа → 200 OK
│   └─ Тела нет (DELETE, PUT/PATCH без возврата) → 204 No Content
│
└─ Нет — чья вина?
    ├─ Клиент
    │   ├─ Нет/невалидный токен → 401
    │   ├─ Токен валидный, но нет прав → 403 (или 404 если скрываем существование)
    │   ├─ Ресурс не существует → 404
    │   ├─ HTTP-метод не поддерживается → 405
    │   ├─ Запрос не распарсился (битый JSON) → 400
    │   ├─ Распарсился, но данные не прошли валидацию → 400
    │   ├─ Конфликт с текущим состоянием сервера → 409
    │   ├─ Превышен rate limit → 429
    │   └─ Ресурс существовал, но удалён навсегда → 410
    │
    └─ Сервер
        ├─ Upstream вернул некорректный ответ → 502
        ├─ Upstream не ответил вовремя (таймаут) → 504
        ├─ Сервер временно недоступен (перегрузка/обслуживание) → 503
        └─ Любая другая необработанная ошибка → 500
```

## 2xx — Успех

### 200 OK

Запрос выполнен, ответ содержит тело.

**Применять когда:**

- `GET` — возвращает данные ресурса
- `PUT` / `PATCH` — обновление с возвратом изменённого ресурса
- `POST` — действие выполнено, но новый ресурс не создан (например, вход в систему, получение токена)

### 201 Created

Новый ресурс создан немедленно.

**Применять когда:** `POST /users`, `POST /posts` — ресурс создан и доступен прямо сейчас.

**Обязательно:** заголовок `Location` с URI созданного ресурса (RFC 7231 §6.3.2).

```
HTTP/1.1 201 Created
Location: /users/456
```

**Не применять:** если создание поставлено в очередь → `202`.

### 202 Accepted

Запрос принят, обработка произойдёт позже (асинхронно).

**Применять когда:** отправка email, фоновая обработка файлов, emit события в другой микросервис.

**Best practice:** вернуть в теле URL для проверки статуса задачи.

```json
{
  "jobId": "abc123",
  "statusUrl": "/jobs/abc123"
}
```

### 204 No Content

Успех, тела ответа нет и быть не должно.

**Применять когда:**

- `DELETE` — ресурс удалён, возвращать нечего
- `PUT` / `PATCH` — обновление без возврата изменённого ресурса

**Важно:** тело ответа при 204 запрещено RFC. `{ "message": "Deleted" }` — нарушение стандарта.

## 3xx — Редиректы

Выбор зависит от двух критериев: **постоянство** и **сохранение HTTP-метода**.

```
Перемещение постоянное?
├─ Да → нужно сохранить метод (POST→POST, PUT→PUT)?
│   ├─ Да → 308 Permanent Redirect
│   └─ Нет → 301 Moved Permanently
└─ Нет (временное) → нужно сохранить метод?
    ├─ Да → 307 Temporary Redirect
    └─ Нет → 302 Found
```

| Код | Постоянное | Метод сохраняется        |
| --- | ---------- | ------------------------ |
| 301 | Да         | Нет (POST→GET допустимо) |
| 302 | Нет        | Нет (POST→GET допустимо) |
| 307 | Нет        | Да                       |
| 308 | Да         | Да                       |

**Для REST API** при переносе эндпоинтов (например, `/v1/` → `/v2/`) используют **308** — метод сохраняется, перенос постоянный.

## 4xx — Ошибки клиента

### 400 Bad Request

Запрос структурно некорректен — сервер не может его распарсить.

**Применять когда:**

- Невалидный JSON (синтаксическая ошибка)
- Неверный `Content-Type`
- Отсутствуют обязательные query-параметры

**Применять также** для ошибок валидации данных (невалидный формат, нарушение бизнес-правил поля).

### 401 Unauthorized

Запрос не аутентифицирован (несмотря на название — это про _аутентификацию_, не авторизацию).

**Применять когда:**

- Заголовок `Authorization` отсутствует
- Токен просрочен или подделан
- API-ключ не существует

**Обязательно:** заголовок `WWW-Authenticate` (RFC 7235).

```
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Bearer realm="api"
```

### 403 Forbidden

Аутентификация прошла успешно, но прав на действие нет.

**Применять когда:**

- Обычный пользователь обращается к `/admin/...`
- OAuth-токен не имеет нужного scope
- Пользователь обращается к чужому ресурсу, факт существования которого не является секретом

**403 vs 404 в security-контексте:**

```
Пользователь может знать, что ресурс существует?
├─ Да (публичный ресурс, просто нет доступа) → 403
└─ Нет (чужие приватные данные — утечка через факт существования) → 404
```

Пример: чужой черновик документа — лучше отдать `404`, чтобы не раскрыть его существование.

### 404 Not Found

Ресурс не существует, либо его существование намеренно скрывается (см. 403 vs 404 выше).

### 405 Method Not Allowed

Ресурс существует, но не поддерживает указанный HTTP-метод.

**Обязательно:** заголовок `Allow` со списком допустимых методов (RFC 7231 §6.5.5).

```
HTTP/1.1 405 Method Not Allowed
Allow: GET, POST, HEAD
```

**Не путать с 404:** если URL не существует вовсе — `404`, не `405`.

### 409 Conflict

Запрос корректен, но конфликтует с текущим состоянием сервера.

**Применять когда:**

- Email уже зарегистрирован (SCIM RFC 7644 прямо предписывает 409)
- Username уже занят
- Конфликт оптимистичной блокировки (несоответствие версий)
- Повторный запрос с тем же `idempotency-key` и другими параметрами (Stripe)
- Попытка совершить действие, невозможное в текущем состоянии (например, отменить уже отменённый заказ)

**409 vs 400:**

```
В чём проблема с данными?
├─ Данные сами по себе некорректны (формат, диапазон, бизнес-правило поля) → 400
└─ Данные корректны, но конфликтуют с состоянием других ресурсов → 409
```

**Тело ответа при 409:**

```json
{
  "statusCode": 409,
  "error": "USER_EMAIL_ALREADY_EXISTS",
  "message": "User with this email already exists"
}
```

- `error` — машиночитаемый код (фронтенд switch-ает по нему для локализации)
- `message` — человекочитаемое описание для разработчиков/логов
- **Не включать** в ответ сам email — enumeration attack

### 410 Gone

Ресурс существовал, но удалён навсегда и не будет восстановлен.

**410 vs 404:**

```
Ресурс не найден
└─ Сервер знает, что ресурс существовал и удалён навсегда?
    ├─ Да → 410
    └─ Нет / неизвестно → 404
```

**Применять когда:** версия API выведена из эксплуатации (`/v1/endpoint` → навсегда удалён), ресурс намеренно удалён с tombstone-записью.

**На практике:** большинство API возвращают `404` — поддержка `410` требует хранить записи об удалённых ресурсах.

**Применять когда:**

- `age: -5` — синтаксически верно, семантически нет
- Невалидный формат email
- `startDate > endDate`
- Ссылка на несуществующий `roleId`

**Тело ответа при 400 (валидация):**

```json
{
  "statusCode": 400,
  "error": "VALIDATION_ERROR",
  "message": "Validation failed",
  "errors": [
    {
      "field": "email",
      "code": "invalid_format",
      "message": "Must be a valid email address"
    },
    {
      "field": "age",
      "code": "out_of_range",
      "message": "Must be greater than 0"
    }
  ]
}
```

### 429 Too Many Requests

Клиент превысил допустимое число запросов за единицу времени.

**Рекомендуемые заголовки:**

```
HTTP/1.1 429 Too Many Requests
Retry-After: 60
X-RateLimit-Limit: 100
X-RateLimit-Remaining: 0
X-RateLimit-Reset: 1712145600
```

## 5xx — Ошибки сервера

### 500 Internal Server Error

Необработанное исключение на сервере — причина неизвестна или не подходит под другие 5xx.

**Не раскрывать** стек-трейс или внутренние детали в ответе клиенту.

### 502 Bad Gateway

Сервер работает в роли прокси/gateway и получил некорректный ответ от upstream-сервиса.

**Применять когда:** API Gateway получил невалидный HTTP-ответ от микросервиса.

### 503 Service Unavailable

Сервер временно не может обрабатывать запросы.

**Применять когда:** плановое обслуживание, перегрузка, circuit breaker открыт.

**Best practice:** заголовок `Retry-After` с временем повторной попытки.

### 504 Gateway Timeout

Сервер-прокси не дождался ответа от upstream в отведённое время.

**502 vs 504:**

```
Upstream ответил?
├─ Да, но ответ некорректный → 502
└─ Нет, истёк таймаут → 504
```

## Сравнение практики крупных компаний

| Ситуация               | Stripe | GitHub  | Google Cloud | AWS Cognito |
| ---------------------- | ------ | ------- | ------------ | ----------- |
| Невалидные данные      | 400    | **422** | 400          | 400         |
| Дублирование ресурса   | 409    | 422     | **409**      | 400         |
| Нет токена / просрочен | 401    | 401     | 401          | 400         |
| Нет прав               | 403    | 403     | 403          | 403         |
| Ресурс не найден       | 404    | 404     | 404          | 404         |
| Rate limit             | 429    | 429     | 429          | 429         |
| Создан ресурс          | 200    | **201** | **201**      | 200         |

Единого стандарта нет, но RFC + подход Google/GitHub покрывают большинство случаев.

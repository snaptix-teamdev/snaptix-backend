# Папка `infrastructure/` на уровне сервиса: зачем и почему

## Контекст

В каждом микросервисе проекта (кроме `gateway`) на одном уровне с `core/` и `modules/`
находится папка `infrastructure/`. Вопрос: это случайность или осознанный архитектурный выбор?

---

## Откуда это пришло: Hexagonal Architecture

Это паттерн **Hexagonal Architecture** (он же **Ports and Adapters**), введённый Аластером
Кокберном в 2005 году. Ключевая идея: приложение изолируется от внешнего мира через **порты**
(интерфейсы) и **адаптеры** (конкретные реализации).

В NestJS-монорепо это выражается на двух уровнях:

### Уровень 1 — Внутри каждого модуля (feature-level)

```
modules/users/
├── api/            ← Входящий адаптер (HTTP)
├── application/    ← Бизнес-логика (use cases)
├── domain/         ← Сущности и правила
├── infrastructure/ ← Исходящие адаптеры (репозитории, внешние сервисы)
└── converter/      ← Маппинг между слоями
```

Здесь `infrastructure/` внутри модуля — это адаптеры конкретного домена:

- `users.repository.ts` — запись/чтение пользователей через Prisma
- `users.query-repository.ts` — оптимизированные read-запросы
- `jwt.adapter.ts` — работа с JWT-токенами (в модуле `auth`)

### Уровень 2 — На уровне всего сервиса (app-level)

```
apps/user-accounts/src/
├── core/           ← NestJS-инфраструктура фреймворка
├── infrastructure/ ← Разделяемые адаптеры к внешним системам
└── modules/        ← Бизнес-фичи
```

Здесь `infrastructure/` — это **разделяемые** адаптеры, которые нужны **нескольким модулям**
сразу и не принадлежат ни одному из них.

---

## Чем `infrastructure/` отличается от `core/`

Это самый частый вопрос, потому что обе папки лежат рядом и обе содержат "технический" код.

| Критерий           | `core/`                                                                    | `infrastructure/`                                                  |
| ------------------ | -------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| **Что хранит**     | NestJS bootstrap: guards, filters, interceptors, decorators, setup, config | Адаптеры к внешним системам: Prisma, Nodemailer, S3, Redis         |
| **Зависит от**     | NestJS framework (`@nestjs/*`)                                             | Конкретных провайдеров (`@prisma/client`, `nodemailer`, `aws-sdk`) |
| **Меняется когда** | Обновляется NestJS или меняется его настройка                              | Меняется провайдер БД, email-сервис, хранилище                     |
| **Кто использует** | Весь сервис (автоматически через middleware/guards)                        | Только те модули, которым нужен DB/email/etc.                      |
| **Пример**         | `AccessTokenGuard`, `GatewayExceptionFilter`, `CorsSetup`                  | `PrismaService`, `EmailService`, `S3Adapter`                       |

### Аналогия

- `core/` — это **каркас здания** (несущие стены, электрика, вентиляция). Меняется редко,
  обеспечивает работу всего.
- `infrastructure/` — это **коммуникации** (трубы до внешней сети, интернет-кабель). Соединяет
  здание с внешним миром.
- `modules/` — это **комнаты** (каждая со своей мебелью и назначением).

## Почему `PrismaService` живёт в `infrastructure/`, а не в `core/`

`PrismaService` — это адаптер к PostgreSQL. Если завтра вы переходите с Prisma на TypeORM или
Drizzle, вы меняете `infrastructure/`, но `core/` не трогаете.

Если положить Prisma в `core/`, то:

1. `core/` начинает смешивать две разные ответственности: «как настроен NestJS» и «с каким
   хранилищем мы работаем».
2. Любой разработчик, смотрящий на `core/`, ожидает там найти фреймворк-специфичный код,
   а не ORM.
3. При смене провайдера (Prisma → TypeORM) вы меняете папку, которая концептуально не должна
   была знать об ORM.

---

## Почему настройку Prisma нельзя вынести в `modules/`

Это ключевой вопрос. Разберём по конкретным причинам.

### 1. Prisma не принадлежит ни одному домену

Модули (`users`, `sessions`, `posts`) — это бизнес-домены. Prisma — технический инструмент,
который **используют все домены**, но не является частью ни одного из них.

Вопрос «в какой модуль положить Prisma?» не имеет правильного ответа, потому что это
неправильный вопрос. Так же как нельзя спросить «в какую комнату положить электрощиток» —
он обслуживает весь дом, а не одну комнату.

### 2. Один connection pool на весь сервис

`PrismaService` под капотом держит **connection pool** к PostgreSQL. Если бы Prisma жила в модуле
`users` и каждый другой модуль создавал бы свой экземпляр — у вас было бы несколько независимых
пулов, конкурирующих за соединения с базой.

Размещение в `infrastructure/` с `@Global()` гарантирует:

```ts
// infrastructure/prisma/prisma.module.ts
@Global() // ← регистрируется один раз в DI-контейнере всего сервиса
@Module({
  providers: [PrismaService, PrismaConfig],
  exports: [PrismaService],
})
export class PrismaModule {}
```

Один `PrismaModule` → один `PrismaService` → один connection pool → все репозитории используют
одно и то же подключение к БД.

### 3. Нарушение инкапсуляции модулей

В NestJS каждый модуль инкапсулирует свою область ответственности. Модуль `users` знает о
пользователях. Модуль `sessions` знает о сессиях. Если `PrismaModule` кладём в `modules/users/`,
то `sessions` вынужден импортировать **из чужого домена**:

```ts
// sessions.module.ts — ПЛОХО
@Module({
  imports: [
    UsersModule, // ← зачем sessions знать о users? только ради PrismaModule!
  ],
})
export class SessionsModule {}
```

Это создаёт **искусственную межмодульную зависимость** там, где её не должно быть. `sessions`
начинает зависеть от `users` не потому, что между ними есть бизнес-связь, а из-за технической
детали реализации.

### 4. Риск циклических зависимостей

Когда модули начинают импортировать друг друга ради общих технических зависимостей, легко
получить циклический граф импортов. NestJS умеет разрешать циклы через `forwardRef()`, но это
костыль, а не решение. Правильный ответ — не создавать такие зависимости.

### 5. `@Global()` не имеет смысла внутри feature-модуля

Декоратор `@Global()` регистрирует провайдеры в глобальном DI-контейнере, чтобы их не нужно
было импортировать явно в каждом модуле. Если поставить `@Global()` на модуль внутри
`modules/users/`, это будет архитектурным противоречием: глобальный провайдер, спрятанный
в локальном бизнес-модуле.

Разработчик, смотрящий на `modules/users/`, не ожидает найти там что-то, влияющее на весь сервис.

### 6. Нарушение принципа единственной ответственности на уровне модуля

Модуль `users` должен отвечать за одно: управление пользователями. Если туда добавить Prisma,
его ответственность расширяется до «управление пользователями + предоставление DB-подключения
всему сервису». Это прямое нарушение SRP.

### Итог: правило выбора расположения

```
Задайте вопрос: «Это принадлежит конкретному домену или всему сервису?»

Принадлежит одному домену → modules/{name}/infrastructure/
  Пример: users.repository.ts, jwt.adapter.ts

Принадлежит всему сервису → infrastructure/
  Пример: PrismaService, EmailService, S3Client
```

## Текущая структура в проекте

### `apps/user-accounts/src/infrastructure/`

```
infrastructure/
├── infrastructure.module.ts   ← Реэкспортирует PrismaModule для всего сервиса
└── prisma/
    ├── prisma.config.ts       ← Конфиг подключения (DATABASE_URL, pool size)
    ├── prisma.module.ts       ← @Global() модуль, делает PrismaService доступным везде
    └── prisma.service.ts      ← Обёртка над PrismaClient с pg-адаптером
```

**Почему это на уровне сервиса, а не внутри модуля:**

`PrismaService` нужен одновременно в `users.repository.ts`, `sessions.repository.ts` и любом
будущем репозитории. Если положить его в `modules/users/infrastructure/`, то:

- `sessions` будет импортировать из чужого модуля — нарушение инкапсуляции.
- Появится искусственная зависимость между несвязанными доменами.

### `apps/notifications/src/infrastructure/`

```
infrastructure/
├── infrastructure.module.ts
└── email/
    ├── email.module.ts
    ├── email.config.ts        ← SMTP-настройки
    ├── application/
    │   └── email.service.ts  ← Отправка писем через Nodemailer
    └── templates/
        ├── confirm-email-registration.hbs
        ├── password-changed.hbs
        └── reset-password.hbs
```

Здесь `infrastructure/` содержит email-адаптер — другой вид внешней системы (SMTP-сервер вместо БД).

## Два уровня `infrastructure/` — схема взаимодействия

```
apps/user-accounts/src/

infrastructure/           ← РАЗДЕЛЯЕМЫЕ адаптеры (уровень сервиса)
└── prisma/
    └── PrismaService    ─────────────────────────────────┐
                                                           │ инжектируется
modules/                                                   │
├── users/                                                 │
│   └── infrastructure/  ← МОДУЛЬНЫЕ адаптеры             │
│       ├── users.repository.ts  ◄──────────────────────── ┘
│       └── users.query-repository.ts  ◄──────────────────┘
│                                                          │
└── sessions/                                             │
    └── infrastructure/                                   │
        └── sessions.repository.ts  ◄─────────────────────┘
```

`PrismaService` создаётся один раз на уровне сервиса и инжектируется в репозитории отдельных
модулей. Это соответствует принципу единственного источника истины для DB-подключения.

## Когда что добавлять в `infrastructure/`

| Что добавляете                 | Куда                                                   |
| ------------------------------ | ------------------------------------------------------ |
| Новый ORM / клиент БД          | `infrastructure/prisma/` или `infrastructure/typeorm/` |
| S3 / облачное хранилище        | `infrastructure/s3/`                                   |
| Redis / кэш                    | `infrastructure/redis/`                                |
| Внешний HTTP-клиент (общий)    | `infrastructure/http/`                                 |
| Репозиторий конкретного домена | `modules/{name}/infrastructure/`                       |
| Guard / Filter / Interceptor   | `core/guards/`, `core/filters/`                        |
| Конфигурация NestJS            | `core/config/`                                         |

## Сравнение: `infrastructure/prisma/` vs `modules/prisma/`

Речь о конкретной альтернативе: вместо отдельной папки `infrastructure/` на уровне сервиса
положить Prisma как выделенный технический модуль прямо в `modules/`:

```
// Альтернатива: modules/prisma/ как самостоятельный модуль
src/
├── core/
└── modules/
    ├── prisma/        ← технический модуль среди бизнес-модулей
    │   ├── prisma.config.ts
    │   ├── prisma.module.ts
    │   └── prisma.service.ts
    ├── users/
    ├── sessions/
    └── auth/
```

### Что работает одинаково

С точки зрения NestJS DI оба варианта эквивалентны. `PrismaModule` с `@Global()` в обоих
случаях регистрирует `PrismaService` в глобальном контейнере — репозитории получают его через
инжекцию без явных импортов. Технической разницы нет.

### В чём реальная разница

#### Семантика папки `modules/`

Папка `modules/` даёт читателю обещание: здесь лежат **бизнес-фичи**. Когда разработчик
открывает её, он ожидает увидеть домены — `users`, `sessions`, `auth`, `posts`.

Увидев там `prisma/`, он столкнётся с когнитивным диссонансом: это фича или технический
инструмент? Почему база данных лежит рядом с пользователями?

```
// Что видит разработчик при modules/prisma/
modules/
├── auth/      ← бизнес-домен
├── prisma/    ← ??? (это что — фича "prisma"?)
├── sessions/  ← бизнес-домен
└── users/     ← бизнес-домен
```

```
// Что видит разработчик при инфраструктурном подходе
infrastructure/
└── prisma/    ← понятно: адаптер к внешней системе

modules/
├── auth/      ← бизнес-домен
├── sessions/  ← бизнес-домен
└── users/     ← бизнес-домен
```

#### Проблема масштабирования

Если Prisma живёт в `modules/prisma/`, то при добавлении Redis, S3 и email-адаптера получается:

```
modules/
├── auth/
├── email/     ← технический
├── posts/
├── prisma/    ← технический
├── redis/     ← технический
├── s3/        ← технический
├── sessions/
└── users/
```

Папка `modules/` превращается в свалку: бизнес-домены перемешаны с техническими адаптерами.
В подходе с `infrastructure/` новые адаптеры просто расширяют уже выделенную папку:

```
infrastructure/
├── email/
├── prisma/
├── redis/
└── s3/

modules/
├── auth/
├── posts/
├── sessions/
└── users/
```

#### Ответ на вопрос «где искать подключение к БД?»

| Подход                   | Путь мысли разработчика                                                                                                       |
| ------------------------ | ----------------------------------------------------------------------------------------------------------------------------- |
| `infrastructure/prisma/` | «Нужно найти подключение к базе» → смотрю в `infrastructure/` → нашёл                                                         |
| `modules/prisma/`        | «Нужно найти подключение к базе» → смотрю в `core/`... нет → смотрю в `infrastructure/`... нет → смотрю в `modules/`... нашёл |

Когда расположение кода совпадает с ожиданием читателя — это хорошая архитектура.

### Итоговое сравнение

| Критерий                                | `infrastructure/prisma/`                        | `modules/prisma/`            |
| --------------------------------------- | ----------------------------------------------- | ---------------------------- |
| Техническое поведение                   | Идентично                                       | Идентично                    |
| Семантика папки соблюдается             | Да                                              | Нет — `modules/` засорён     |
| Масштабируемость (Redis, S3...)         | Добавляются в `infrastructure/`                 | Засоряют `modules/`          |
| Дискаверабилити для нового разработчика | Очевидно                                        | Неочевидно                   |
| Соответствие Hexagonal Architecture     | Да                                              | Частично                     |
| Количество top-level папок              | Больше (`core/`, `infrastructure/`, `modules/`) | Меньше (`core/`, `modules/`) |

Единственное преимущество `modules/prisma/` — меньше top-level папок. Это не архитектурный
аргумент, а эстетический. При росте проекта семантическая ясность важнее лаконичности структуры.

## Сравнение: `modules/` как группировка vs плоская структура в `src/`

Ещё одна альтернатива — убрать папку `modules/` вообще и положить все бизнес-модули
напрямую в `src/`:

```
// Плоская структура
src/
├── core/
├── infrastructure/
├── auth/           ← был modules/auth/
├── sessions/       ← был modules/sessions/
└── users/          ← был modules/users/
```

Это **легитимный подход**. Официальная документация NestJS и большинство туториалов используют
именно плоскую структуру. Технически разницы нет никакой.

### Что добавляет папка `modules/`

`modules/` — это не требование NestJS, а **конвенция группировки**. Она добавляет один уровень
вложенности и одно обещание читателю: «всё, что лежит здесь — бизнес-домен».

Без неё `src/` выглядит так:

```
src/
├── auth/           ← бизнес-домен
├── core/           ← NestJS-инфраструктура
├── infrastructure/ ← внешние адаптеры
├── sessions/       ← бизнес-домен
└── users/          ← бизнес-домен
```

Разработчику нужно самому разобраться, что из этого относится к бизнес-логике, а что — к
технической обвязке. Папка `modules/` снимает эту неоднозначность сразу.

### Когда плоская структура работает лучше

Плоская структура выигрывает в **небольших сервисах** с 2–4 доменами. Здесь выгода очевидна:

- Меньше уровней вложенности → короче пути импортов (`../users/` вместо `../../modules/users/`)
- Меньше папок-обёрток без собственного кода
- Быстрее ориентироваться в файловом дереве

При таком масштабе `src/` с 5–6 папками читается легко, и дополнительная группировка
только добавляет шум.

### Когда `modules/` как группировка необходима

При росте сервиса плоская структура начинает проигрывать. Представьте зрелый `user-accounts`
с 10+ доменами:

```
// Плоская структура при масштабировании
src/
├── auth/
├── billing/
├── core/           ← технический
├── devices/
├── infrastructure/ ← технический
├── notifications/
├── permissions/
├── posts/
├── profiles/
├── sessions/
├── subscriptions/
├── users/
└── verification/
```

Здесь `core/` и `infrastructure/` теряются среди бизнес-доменов. Новый разработчик не может
за секунду понять структуру сервиса — ему нужно читать каждую папку.

```
// С группировкой modules/
src/
├── core/           ← понятно: NestJS-инфраструктура
├── infrastructure/ ← понятно: внешние адаптеры
└── modules/        ← понятно: всё бизнес-логика
    ├── auth/
    ├── billing/
    ├── devices/
    ├── notifications/
    ├── permissions/
    ├── posts/
    ├── profiles/
    ├── sessions/
    ├── subscriptions/
    ├── users/
    └── verification/
```

Три папки в `src/` — три концепции. Открыл, понял, пошёл дальше.

### Ключевая зависимость: контекст проекта

Этот выбор во многом определяется тем, что уже есть рядом в `src/`. Если в `src/` уже живут
`core/` и `infrastructure/` (как в этом проекте), то без `modules/` бизнес-домены
**смешиваются** с техническими папками в одном пространстве. Папка `modules/` в таком
контексте не лишний уровень — она закрывает третью категорию в явно читаемой схеме:

```
src/ содержит три типа вещей:
  core/           → как работает фреймворк
  infrastructure/ → с чем соединяется сервис
  modules/        → что делает сервис
```

Если бы в `src/` не было `core/` и `infrastructure/`, аргумент в пользу `modules/` был бы
значительно слабее.

### Итоговое сравнение

| Критерий                          | `src/modules/{name}/`                      | `src/{name}/` (плоско)           |
| --------------------------------- | ------------------------------------------ | -------------------------------- |
| Уровней вложенности               | Больше на 1                                | Меньше                           |
| Длина путей импортов              | Длиннее                                    | Короче                           |
| Читаемость при 3–5 доменах        | Одинакова                                  | Одинакова                        |
| Читаемость при 10+ доменах        | Чище (`modules/` группирует)               | `src/` становится перегружен     |
| Разделение бизнес/технический код | Явное                                      | Требует знания проекта           |
| Соответствие NestJS-документации  | Нет (docs используют плоскую)              | Да                               |
| Применимость в данном проекте     | Уместна (есть `core/` и `infrastructure/`) | Требует переосмысления структуры |

### Вывод по этому вопросу

Плоская структура — не ошибка, а осознанный выбор с реальными преимуществами. Но в контексте

## Вывод

Папка `infrastructure/` на уровне сервиса — **осознанный архитектурный выбор**, а не случайность.
Она отвечает за адаптеры к внешним системам, которые разделяются между модулями, и чётко отделена
от `core/` (который отвечает за NestJS-фреймворк) и `modules/` (которые отвечают за бизнес-логику).

Такое разделение даёт:

1. **Заменяемость** — смена Prisma на другой ORM затрагивает только `infrastructure/`.
2. **Читаемость** — любой новый разработчик сразу понимает, где искать подключение к БД.
3. **Масштабируемость** — новые внешние адаптеры (Redis, S3) добавляются в одно место без
   загрязнения `core/` или конкретных модулей.

# Выбор транспорта для billing: вызовы из gateway, вебхуки и события

> **Решение:** HTTP — для синхронных вызовов gateway → billing и для вебхуков платёжного провайдера.
> RabbitMQ — для событий из billing в другие сервисы.
> Рассматривались: Nest-TCP, HTTP, gRPC, tRPC, RabbitMQ (в том числе RPC через брокер).

## Контекст

`billing` — новый микросервис (SNAP-120). В остальных сервисах сейчас так:

- gateway → сервисы — **Nest-TCP** (`ClientsModule` + `Transport.TCP` в `apps/gateway/src/modules/gateway/gateway.module.ts`);
- события между сервисами — **RabbitMQ** через `@golevelup/nestjs-rabbitmq`: topic exchange на сервис, outbox в `posts`, dead-letter в `files`.

У billing три разных вида взаимодействия, и один транспорт им всем не подходит:

| #   | Взаимодействие                   | Пример                                                         | Что важно                                |
| --- | -------------------------------- | -------------------------------------------------------------- | ---------------------------------------- |
| 1   | gateway ждёт ответ               | «создать платёж → вернуть ссылку на оплату», «статус подписки» | задержка, понятные ошибки, таймауты      |
| 2   | Платёжный провайдер вызывает нас | вебхук «платёж прошёл»                                         | провайдер умеет **только HTTP**          |
| 3   | billing сообщает другим сервисам | `subscription.activated`, `payment.failed`                     | надёжная доставка, несколько получателей |

## Итог

| Взаимодействие              | Транспорт                                        | Почему                                                                         |
| --------------------------- | ------------------------------------------------ | ------------------------------------------------------------------------------ |
| 1. gateway → billing        | **HTTP**                                         | тот же сервер, что и для вебхуков; просто отлаживать; без новой инфраструктуры |
| 2. Провайдер → billing      | **HTTP**                                         | других вариантов нет                                                           |
| 3. billing → другие сервисы | **RabbitMQ** (topic exchange `billing.exchange`) | асинхронно, fan-out, повторы; уже используется в проекте                       |

## Варианты

### 1. Nest-TCP (как сейчас у остальных сервисов)

**Принцип.** Собственный протокол Nest: JSON с префиксом длины поверх TCP. Запрос — `client.send(pattern, data)`, обработчик — `@MessagePattern(pattern)`.

**Плюсы:**

- уже используется, ноль новой инфраструктуры;
- нативно для Nest: pipes, фильтры, `MicroserviceExceptionFilter` работают.

**Минусы:**

- протокол понимает только Nest;
- контракт типизирован лишь приведением `send<T>()`;
- нет дедлайнов, только таймаут rxjs на клиенте.

**Риски для Snaptix:**

- клиент держит одно постоянное соединение, поэтому весь трафик с пода gateway уходит в один под сервиса (как у gRPC);
- вебхукам всё равно нужен отдельный HTTP-порт.

**Вердикт:** самый дешёвый вариант, но ничего не даёт сверх HTTP, а порта для billing понадобится два.

---

### 2. HTTP ✅ выбран

**Принцип.** Обычное Nest-приложение: `NestFactory.create` + `app.listen(PORT)`, контроллеры с `@Get`/`@Post`. gateway вызывает его через axios. Отдельного «HTTP-транспорта» в `@nestjs/microservices` нет, потому что это стандартный режим Nest.

**Плюсы:**

- вебхуки и вызовы gateway — на одном сервере и одном порту;
- curl, читаемые логи, стандартные прокси и балансировка;
- работает с любым языком.

**Минусы:**

- типизированного клиента нет, контракт держится на общих Zod-схемах и DTO из `libs/contracts`;
- дедлайны и повторы — вручную на клиенте.

**Риски для Snaptix:**

- `MicroserviceExceptionFilter` не работает в HTTP-контексте (это `RpcExceptionFilter`), нужен свой HTTP-фильтр;
- в gateway появится второй стиль клиентов рядом с TCP.

**Вердикт:** лучший баланс для billing — вебхуки всё равно требуют HTTP.

---

### 3. gRPC

**Принцип.** RPC поверх HTTP/2, контракт в `.proto`, бинарный protobuf. В Nest — `Transport.GRPC` + `@GrpcMethod`, клиент — `ClientGrpc.getService<T>()`.

**Плюсы:**

- строгий контракт с кодогенерацией;
- совместимость версий за счёт номеров полей;
- встроенные дедлайны, стандартные коды ошибок, метаданные (хедеры), стриминг;
- health-протокол для k8s-проб;
- любые языки.

**Минусы:**

- `.proto` + кодогенерация (`ts-proto`), `@grpc/grpc-js`, `@grpc/proto-loader`;
- контракт описан дважды (proto и Zod);
- отладка через grpcurl;
- вебхукам нужен второй порт.

**Риски для Snaptix:**

- балансировка в k8s: HTTP/2 держит одно соединение, ClusterIP балансирует по соединениям — нужен headless Service + `round_robin` или service mesh;
- строковый `code` в `IDomainError` не ложится на числовые gRPC-статусы — нужен маппинг в обе стороны;
- proto3 не знает `null` и `Decimal` (деньги — `int64` в копейках или строкой);
- `.proto` должен попасть в `dist` и Docker-образ (`assets` в `nest-cli.json`).

**Вердикт:** самый «продакшен» вариант для синхронных вызовов между сервисами. Стоит вернуться к нему, если синхронных вызовов станет много или появятся сервисы не на TS.

---

### 4. tRPC

**Принцип.** TypeScript-фреймворк поверх HTTP + JSON. Сервер описывает роутер процедур (`query`/`mutation`/`subscription`) с Zod-валидацией. Клиент импортирует **только тип** роутера и получает полностью типизированные вызовы без кодогенерации.

**Плюсы:**

- сквозная типизация без схем и кодогенерации;
- Zod как родной валидатор;
- обычный HTTP, вебхуки на том же порту;
- батчинг запросов;
- superjson сохраняет `Date`, `BigInt`, `undefined`.

**Минусы:**

- только TypeScript с обеих сторон;
- нет версионирования схемы;
- рассчитан на full-stack, где клиент и сервер деплоятся вместе;
- нет официальной интеграции с NestJS.

**Риски для Snaptix:**

- работает **рядом** с Nest: глобальные pipes, фильтры, guards и interceptors на процедуры не действуют;
- `import type { BillingRouter }` связывает сборку gateway с исходниками billing вплоть до его Prisma-клиента;
- при независимом деплое типы, совпавшие при компиляции, могут разойтись в рантайме.

**Вердикт:** хорош для TS-фронтенда, который ходит в бэкенд напрямую. Для связи микросервисов в этом репо подходит хуже остальных.

---

### 5. RabbitMQ: всё через брокер, включая RPC

**Принцип.** gateway публикует запрос в очередь, сервис отвечает через reply-queue с `correlation_id`. В `@golevelup` это `amqp.request()` и `@RabbitRPC()`.

**Плюсы:**

- не нужно знать адреса сервисов;
- автоматическая балансировка между потребителями;
- буферизация пиков;
- хедеры и метаданные AMQP (`headers`, `correlation_id`, `message_id`, `expiration`).

**Минусы:**

- лишний переход через брокер на каждый запрос;
- брокер становится единой точкой отказа для **всего** пользовательского трафика;
- сложнее отладка и трейсинг.

**Риски для Snaptix:**

- **запрос, на который уже никто не ждёт ответа:** gateway вернул 504, а запрос остался в очереди и будет исполнен — для billing это двойное списание;
- at-least-once — обработчики должны быть идемпотентны;
- «отравленные» сообщения без DLX;
- неограниченный рост очередей;
- нет гарантии порядка при нескольких потребителях.

**Вердикт:** для синхронных вызовов — нет. Для **событий** — да, это и выбрано (взаимодействие 3).

## `null`, `undefined` и отсутствующее поле

Проверено на практике: axios 1.15 → Express 5 (внутри Nest 11), Zod 4.3.

### Что получает другая сторона (тело запроса, JSON)

| Отправили                          | По сети                      | Получили                                                                     |
| ---------------------------------- | ---------------------------- | ---------------------------------------------------------------------------- |
| `{}` (поле не передали)            | `{}`                         | поля нет, `body.name === undefined`                                          |
| `{ name: undefined }`              | `{}`                         | **поля нет** — неотличимо от предыдущего                                     |
| `{ name: null }`                   | `{"name":null}`              | `{ name: null }` — **null сохраняется**                                      |
| `{ profile: { name: undefined } }` | `{"profile":{}}`             | вложенное поле тоже пропало                                                  |
| `{ tags: [1, undefined, null] }`   | `[1,null,null]`              | в массиве `undefined` → **`null`**                                           |
| `{ n: NaN, inf: Infinity }`        | `{"n":null,"inf":null}`      | **`NaN`/`Infinity` → `null`**                                                |
| `{ d: new Date(0) }`               | `"1970-01-01T00:00:00.000Z"` | **строка**, не `Date`                                                        |
| `{ big: 1n }`                      | —                            | axios падает до отправки: `TypeError: Do not know how to serialize a BigInt` |

Ответ сервера ведёт себя так же: `res.json({ a: undefined, b: null })` → у клиента `{ b: null }`.

**GET-параметры:**

- `null` и `undefined` axios **выкидывает целиком**;
- всё остальное приходит строками (`0` → `"0"`, `false` → `"false"`);
- массив уходит как `arr[]=1&arr[]=2`, и Express 5 кладёт его под ключ `"arr[]"`.

Передать `null` через query-строку нельзя.

### По транспортам

| Транспорт               | Сериализация                                                      | Поведение                                                                                 |
| ----------------------- | ----------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| HTTP (axios)            | `JSON.stringify` / `JSON.parse`                                   | как в таблице выше                                                                        |
| Nest-TCP                | `JSON.stringify` (`@nestjs/microservices/helpers/json-socket.js`) | так же                                                                                    |
| RabbitMQ (`@golevelup`) | `JSON.stringify` (сериализатор по умолчанию)                      | так же                                                                                    |
| gRPC (proto3)           | protobuf                                                          | `null` и «не передали» → значение по умолчанию (`""`, `0`) или «не задано» для `optional` |
| tRPC + superjson        | superjson                                                         | `undefined`, `Date`, `BigInt` сохраняются                                                 |

### Zod на стороне получателя

| Схема                       | `{}` (не передали)                                  | `{ name: null }`    |
| --------------------------- | --------------------------------------------------- | ------------------- |
| `z.string()`                | ❌                                                  | ❌                  |
| `.optional()`               | ✅ `{}`                                             | ❌ **ошибка**       |
| `.nullable()`               | ❌ **ошибка** `expected string, received undefined` | ✅ `{ name: null }` |
| `.nullish()`                | ✅ `{}`                                             | ✅ `{ name: null }` |
| `.nullable().optional()`    | ✅ `{}` (ключа нет)                                 | ✅ `{ name: null }` |
| `.nullable().default(null)` | ✅ `{ name: null }`                                 | ✅ `{ name: null }` |

Пример из проекта: `clientDetailsSchema.ip` — `z.string().nullable()`. В gateway `ExtractClientDetails` делает `request.ip ?? null`. Без `?? null` ключ `ip` пропал бы при сериализации, и логин падал бы с `VALIDATION_ERROR`.

### Prisma на стороне получателя

- **`update`**: `{ name: undefined }` — не трогать поле, `{ name: null }` — записать `NULL`. Для PATCH это даёт три состояния: нет поля / `null` / значение. Но `.nullable().default(null)` в PATCH-схеме превратит «не менять» в «очистить».
- **`where`**: `findMany({ where: { userId: undefined } })` — условие **игнорируется**, возвращаются **все строки**. Если `userId` не дошёл до billing, получим платежи всех пользователей.
- **Деньги**: `Prisma.Decimal` через JSON уходит строкой, `BigInt` не сериализуется вовсе.

### Правила для контрактов

1. Отправитель шлёт `null` **явно** для nullable-полей (`value ?? null`) и не полагается на `undefined`.
2. Схемы на приёме:
   - создание — `.nullable()` или `.nullable().default(null)`;
   - PATCH — `.nullable().optional()`;
   - `.nullish()` — только осознанно.
3. Даты принимать через `z.coerce.date()`, деньги — строкой или целыми копейками, числа проверять на `NaN` до отправки.
4. Не передавать в Prisma `where` поля, которые Zod не проверил как обязательные.

## Что следует из решения

- **HTTP-фильтр исключений в billing.** Формат ответа как у `GatewayExceptionFilter`: `{ errors: [{ status, code, field, message }] }`, чтобы gateway мог проксировать ошибки без преобразований.
- **События — через outbox**, как в `posts`: «записать в БД и опубликовать» не атомарно, без outbox события будут теряться.
- **Вебхуки идемпотентны**: провайдер повторяет доставку, обработка по `event_id` провайдера.
- **Ключ идемпотентности** на командах gateway → billing, которые создают платежи, — защита от повторов при таймаутах.
- **Клиент в gateway** — axios с явным `timeout`; ошибки billing пробрасываются наружу как есть.

## Когда пересмотреть решение

- Синхронных вызовов gateway → billing (или между сервисами) станет много, и понадобятся дедлайны, совместимость версий и строгий контракт → **gRPC**.
- Появится сервис не на TypeScript → **gRPC** или HTTP с OpenAPI.
- Появится TS-фронтенд, который ходит в бэкенд напрямую → можно рассмотреть **tRPC** для этой связи.
